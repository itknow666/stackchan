# 网络语音卡顿对照

状态：二〇二六年十一月十六日的实验候选，正常聊天听感已由用户确认改善；另有一次非致命看门狗告警需要跟进，暂不合入主分支。

用户反馈摸头和固定场景录音流畅，正常聊天回答卡顿。在实际三十秒故事回答期间，设备日志显示二十四千赫、六十毫秒的网络音频每秒到达约十七帧，实际输出只有十三到十五帧。解码队列由两帧增长到十九帧，随后每秒丢弃一到五帧；PCM 输出队列保持满载。

同一过程中，单帧解码最高约十七到十九毫秒，输出写入最高九十三到一百五十九毫秒。独立云端对照通过实际语音识别、模型及语音合成收到二百三十二帧，收包间隔中位数五十九点九八毫秒、最高一百零二点零五毫秒，没有超过一百二十毫秒的间隔。这个对照不能替代机器人所在 Wi-Fi 链路，但设备队列持续积压已经说明播放消费速度不足。

当前假设是输出任务优先级四低于 Opus 解码的五，在忙碌网络播放期间不能及时补充 DMA。候选仅将音频输出任务优先级从四调至六，覆盖启用和禁用音频处理器的两个分支；解码仍为五，其他音频和网络配置不变。输出写入正常阻塞等待 DMA，不能据此推断它会持续独占 CPU。

已完成的检查：完整私有固件构建、刷写校验、Agent 自动启动、SD 三十一段有效、蓝牙重新连接，以及静音实机混合采样率播放、取消和随后新播放。没有观察到崩溃；原音量在静音测试后恢复。

后续真实网络播放记录显示：蓝牙连接时输出恢复每秒约十七帧，解码队列没有持续积压，记录中的收包丢帧计数均为零，输出写入通常最高五十九到六十毫秒。用户确认三十秒故事的声音已连续流畅。这支持提高输出优先级改善了已复现的播放消费不足问题。

同轮长回答中另观察到一次非致命 Task WDT 告警，未导致重启；告警指出 CPU 零的空闲任务没有及时运行，当时为优先级八的 audio_input，回溯位于 AFE 的 AEC 处理。该告警与本次输出优先级改动的因果关系尚未确定，不能凭回溯认定是输出任务自身卡死。后续需记录输入与 AFE 处理负载，完成持续对话验证后再决定合并；不以关闭看门狗代替定位。
