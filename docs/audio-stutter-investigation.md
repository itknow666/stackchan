# 网络语音卡顿对照

状态：二〇二六年十一月十六日的实验候选。最新调度改动已通过一次真实长回答复现验收：声音流畅、无丢帧，原先的输入任务看门狗告警未再出现。持续稳定性仍需单独验证，暂不合入主分支。

用户反馈摸头和固定场景录音流畅，正常聊天回答卡顿。在实际三十秒故事回答期间，设备日志显示二十四千赫、六十毫秒的网络音频每秒到达约十七帧，实际输出只有十三到十五帧。解码队列由两帧增长到十九帧，随后每秒丢弃一到五帧；PCM 输出队列保持满载。

同一过程中，单帧解码最高约十七到十九毫秒，输出写入最高九十三到一百五十九毫秒。独立云端对照通过实际语音识别、模型及语音合成收到二百三十二帧，收包间隔中位数五十九点九八毫秒、最高一百零二点零五毫秒，没有超过一百二十毫秒的间隔。这个对照不能替代机器人所在 Wi-Fi 链路，但设备队列持续积压已经说明播放消费速度不足。

当前假设是输出任务优先级四低于 Opus 解码的五，在忙碌网络播放期间不能及时补充 DMA。候选仅将音频输出任务优先级从四调至六，覆盖启用和禁用音频处理器的两个分支；解码仍为五，其他音频和网络配置不变。输出写入正常阻塞等待 DMA，不能据此推断它会持续独占 CPU。

已完成的检查：完整私有固件构建、刷写校验、Agent 自动启动、SD 三十一段有效、蓝牙重新连接，以及静音实机混合采样率播放、取消和随后新播放。没有观察到崩溃；原音量在静音测试后恢复。

后续真实网络播放记录显示：蓝牙连接时输出恢复每秒约十七帧，解码队列没有持续积压，记录中的收包丢帧计数均为零，输出写入通常最高五十九到六十毫秒。用户确认三十秒故事的声音已连续流畅。这支持提高输出优先级改善了已复现的播放消费不足问题。

同轮长回答中另观察到一次非致命 Task WDT 告警，未导致重启；告警指出 CPU 零的空闲任务没有及时运行，当时为优先级八的 audio_input，回溯位于 AFE 的 AEC 处理。该告警与本次输出优先级改动的因果关系尚未确定，不能凭回溯认定是输出任务自身卡死。后续需记录输入与 AFE 处理负载，完成持续对话验证后再决定合并；不以关闭看门狗代替定位。

设备备份、日志、声音与私有固件二进制均保留在私有运行目录，不随本文件发布。稳定槽位和上个候选镜像保留供回退。

最新复现补充：用户再次反馈 Codex 任务确认回复卡顿。网络输入仍约每秒十七帧，但解码仅十三至十五帧，单帧耗时最高约一百八十七毫秒；解码队列持续积压至十九至二十帧并丢帧，PCM 队列为空。输出写入恢复为正常范围，但等待解码结果的时间增加。此时解码任务运行在零号核心；再次出现 IDLE0 看门狗告警，当时零号核心运行 audio_input，另一核心为空闲任务。

下一对照候选保留输出优先级六、解码优先级五，仅将 Opus 编解码任务在双核设备固定至一号核心，单核配置仍使用零号核心。目的是验证输入 AFE 与解码争用核心的假设。尚未完成实机听感和长对话验证，不能认定已解决卡顿或输入任务的看门狗问题；不关闭看门狗，也不扩大队列来掩盖丢帧。

实机验证结果：用户确认 Codex 任务确认与普通聊天两段都已流畅。对应记录中，解码运行在一号核心，稳定约每秒十七帧，单帧解码最高二十一毫秒；解码队列最多一帧，记录的丢帧计数均为零，未发现崩溃。这支持将编解码与 AFE 输入分配到不同核心解决本次复现的解码饥饿。

仍有独立待处理项：同次记录出现三次 IDLE0 看门狗告警，当时运行 audio_input，未重启。声音流畅不等于输入负载问题已解决；当前继续保留为候选，不据此宣称长时间运行稳定或合入主分支。

输入任务进一步定位：仅加耗时记录的对照版在真实长故事期间再次触发告警。每约一秒，AFE Feed 路径占九百五十至九百七十毫秒，输入读取只占约四十至五十毫秒；处理每秒约一万五千多样本，采音任务几乎不再等待 I2S。待机时 Feed 约四百五十毫秒，正常听取阶段约十毫秒，说明问题集中在播放期间的回声处理。

新候选不关闭看门狗、不更换 AEC 算法，也不调整已验收的解码核心和播放优先级。在每次 Feed 释放内部锁之后，每二百五十毫秒最多主动阻塞一个系统时隙，使空闲任务和低优先级任务可以运行；使用系统时钟差值处理计数回绕。同时保留有界耗时记录，用于核对实际输入吞吐量。完整固件构建、公开补丁与私有 SDK 十七个文件一致性，以及九项主机检查通过，已刷入候选。真实长回答负载验证仍在进行，不以待机没有告警代替播放期间验收。

新候选的实际长回答验收：记录说话状态持续约四十八秒，覆盖原先十秒后就会反复告警的负载区间。没有出现看门狗告警、崩溃或音频丢帧，解码队列最多一帧；两个核心的空闲任务仍由十秒看门狗监测。用户确认故事讲完整且流畅，表情和声音更同步。播放期间仍在持续进行 AFE 回声处理，新增主动阻塞每秒约三至四次，正常听取阶段仍按约每秒一万六千样本采集。该结果支持本次调度饥饿的修复，但不能替代长时间或二十轮对话稳定性验证。
