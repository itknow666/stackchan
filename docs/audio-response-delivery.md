# 长回答与表情启动时机

二〇二六年十一月十六日，用户反馈一分钟故事中途停止，以及表情先出现、过一会儿才有声音。分别确认了两个问题。

## 长回答尾部丢失

兼容接口一次返回整段 PCM，云端迅速编码后放入最多六百帧的队列；设备每六十毫秒消费一帧。原逻辑队列满就丢帧，因此一次生成超过约三十六秒的回答时，后面的内容可能消失。此次实机故事对应的云端日志确有大量队列满告警，机器人随后正常回到听取状态，没有重启。

现在队列满时等待消费，逐帧保持顺序；填充预缓冲时就启动播放，避免生产者等满队列、消费者却尚未启动。兼容接口传递本轮取消上下文，取消或断线能退出等待，已取消的回复不再发送结束事件覆盖后续对话。编码器最后不足一帧的尾音也等待入队。

## 表情提前

原来模型给出文本后立即触发开始事件，九百毫秒的预缓冲计时可能在语音合成完成前就发送表情与说话状态。现在兼容接口先等待语音合成完成，再开始播放阶段；姿态、表情与说话状态仍从同一播放入口发送。识别、模型和合成的总等待并没有因此消失，改善的是表情与声音的启动时机。

## 验证

新增检查使用六十一秒的合成 PCM 和仅一帧容量的队列，确认所有完整帧都交付，没有靠扩大队列避开问题；另检查满队列时可取消。时序与取消测试在旧兼容接口实现上失败、修复后通过。完整 Go 测试、AI 服务竞态检查及构建通过，实际二百二十一条私人录音校验通过。

云端代码已安装，语音包、角色、凭据和网关配置保持原值。用户再次实测后确认故事讲完整且流畅，表情和声音更同步。相应机器人播放状态持续约四十八秒，音频队列没有持续积压，记录的丢帧计数为零。

同次固件候选增加采音任务的有界主动阻塞，解决此前播放时空闲任务长时间得不到运行机会的问题；这轮长回答未再出现原先的看门狗告警。固件改动与长期稳定性边界仍单独记录于草稿 PR #1，不在本云端改动里混入固件代码。
